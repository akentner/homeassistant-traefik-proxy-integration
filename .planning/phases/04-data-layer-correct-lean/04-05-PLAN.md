<assumption_delta_decision>
The orchestrator's detector fired on the word "custom" (false positive), but this plan genuinely introduces a second and third authentication mode. Identity-model answer:
- Primary noun now: `Auth` (an authentication mode plus its credentials), replacing the bearer-only `api_key` string inside the client.
- Decision: `promote` at the client boundary. `TraefikProxyApiClient` only knows `Auth`; bearer is one variant of it, not the default shape.
- Entry data still stores `api_key` until Phase 7 (FLOW-01 auth selector + minor-version config-entry migration). `auth_from_entry_data` is the single translation seam; this add-alongside at the storage layer is accepted, tracked debt that Phase 7 removes by migrating entries to an explicit auth mode. What forces the promote there: the first entry that needs basic auth.
- Suggested invariant test (included in Task 2): every AuthMode round-trips through `TraefikProxyApiClient` to the exact Authorization header on a real request; a future change that reintroduces a bearer-only assumption turns it red.
</assumption_delta_decision>

| Integration -> Traefik API over the network | Credentials leave HA in the Authorization header |
| HA shared aiohttp session | One session object is shared by every integration in the HA process |
